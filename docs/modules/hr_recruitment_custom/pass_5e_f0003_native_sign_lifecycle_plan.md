## 1. Purpose

This document locks the Pass 5E plan for F-0003 Required Documents Checklist, including the already completed F-0003 model/PDF work and the planned native Odoo Sign lifecycle foundation.

The purpose is to preserve the design decisions and discoveries before implementation of Pass 5E-3A, so that:

1. F-0003 remains technically stable and legally traceable.
2. Native Odoo Sign becomes the canonical signing path where SaaS allows it.
3. Manual signed-attachment writeback remains an explicit fallback, not an accidental architecture.
4. The successful one-signer pattern can later be reused for F-0002 and extended to the two-signer F-0004 declaration.
5. Lessons learned from implementation and traceback loops can be appended without re-litigating the whole architecture.

## 4. Canonical signature lifecycle target

The canonical architecture is:

```text
Generated controlled PDF
→ stable signature geometry
→ native Odoo Sign request created/sent
→ signer receives/signs through Odoo Sign
→ signed artifact and certificate generated by Odoo Sign
→ recruitment document registry closes as signed
→ parent applicant workflow gates read registry state only
```

The recruitment document registry is the authority. Source records such as interview evaluation, document checklist, declarations, TORs, board decisions, and contracts are lifecycle sources, not final gate authorities.

---

## 5. Manual fallback lifecycle

Manual fallback remains available:

```text
Generated controlled PDF
→ user signs through manual Odoo Sign flow or outside signing process
→ signed PDF uploaded/attached
→ signed attachment selected on source record
→ registry signed state updated by automation
```

This is not the target architecture. It is retained for operational continuity if native Sign automation is blocked by SaaS restrictions, server-action safe-eval constraints, missing fields, or version drift.

## 6. Native Odoo Sign discovery summary

### 6.1 Confirmed product capability

Native Odoo Sign supports:

* Prepared documents with required/optional fields.
* One-off documents.
* Templates.
* One or more signers.
* Signer roles.
* Signing order.
* Signed document generation.
* Certificate of completion generation.
* Email delivery of final signed artifacts after all signers complete.

### 6.2 Confirmed manual F-0003 test

Manual F-0003 test confirmed:

* Odoo Sign is installed and operational on the Marsellia Enterprise SaaS database.
* Generated F-0003 PDF can be uploaded/prepared in Sign.
* Reviewer role can be created and used.
* Signature field can be placed inside the F-0003 reviewer signature block.
* Signature request email is delivered.
* Signing URL opens correctly.
* Signer can adopt/draw a signature.
* Signer can validate and send completed document.
* Certificate of completion is generated.
* Signed document integrity is valid.

### 6.3 Key runtime sample

Manual F-0003 request sample showed:

```text
sign.request id: 7
state: signed
template_id: 11
request_item_ids: [8]
completed_document_ids: [6]
reference_doc: documents.document,23
reference: <F-0003 PDF filename>
```

Signer item sample showed:

```text
sign.request.item id: 8
partner: Hamam Elfassi
role: Reviewer
email: hamam@marsellia.com
state: completed
signing_date: 2026-05-07
```

Important interpretation:

```text
reference_doc = documents.document,23
```

The manual flow was Documents-app centered. Therefore, the automated HR lifecycle must not rely on applicant/checklist chatter return. It must store and sync `sign.request` references explicitly through the recruitment registry.

## 7. Confirmed Sign data model contracts

### 7.1 `sign.template`

Known useful fields:

```text
name
user_id
folder_id
message
signature_request_validity
model_id
sign_item_role_ids
document_ids
sign_item_ids
```

Implementation decision:

* Create a dynamic applicant-specific template for each generated F-0003 signing request.
* Set minimal safe fields.
* Do not attempt reusable static template for dynamic QWeb PDFs at this stage.

### 7.2 `sign.document`

Known required fields:

```text
attachment_id
template_id
```

Implementation decision:

* Create one `sign.document` from the existing generated F-0003 PDF attachment.
* Do not regenerate the report inside the Sign action.

### 7.3 `sign.item`

Known required/important fields:

```text
document_id
type_id
responsible_id
page
posX
posY
width
height
alignment
required
name
constant
option_ids
transaction_id
```

Implementation decision:

* Use `document_id`, not `template_id`, for creation.
* Use the Signature field type.
* Use the Reviewer role.
* Use actual tested F-0003 reviewer signature coordinates.

### 7.4 `sign.item.type`

Known signature type:

```text
sign.sign_item_type_signature
```

Implementation decision:

* Resolve with `env.ref('sign.sign_item_type_signature')`.

### 7.5 `sign.item.role`

Known roles include:

```text
Reviewer
Applicant
Department Manager
Employee
Customer
Signer 1
```

Manual F-0003 role sample:

```text
Reviewer role id: 18
name: Reviewer
signer_type: fixed
assign_to: false
```

Implementation decision:

* Do not hardcode role ID 18.
* Search for role name `Reviewer`.
* Fail clearly if absent.
* Do not use `assign_to` for F-0003; actual signer mapping belongs in the send request signer row.

### 7.6 `sign.send.request`

Known fields:

```text
template_id
signer_id
signer_ids
subject
body
attachment_ids
model
res_ids
certificate_reference
validity
reminder
set_sign_order
```

Implementation decision:

* Use `sign.send.request` as the send wizard/orchestrator.
* Do not create `sign.request` directly.
* Call `send_request()` and ignore the return value.
* Find the generated `sign.request` after sending.

### 7.7 `sign.send.request.signer`

Known fields:

```text
sign_send_request_id
role_id
partner_id
mail_sent_order
```

Implementation decision:

* Create one signer row for the Reviewer role.
* Partner comes from F-0003 reviewer user partner.
* No signing order for F-0003 single-signer probe.

### 7.8 `sign.request`

Known useful fields:

```text
template_id
state
request_item_ids
completed_document_attachment_ids
completed_document_ids
completion_date
attachment_ids
reference_doc
reference
send_channel
```

Implementation decision:

* Store the generated `sign.request` reference on the recruitment document registry.
* Later sync completion state and artifacts from this request.
* Do not rely on `reference_doc` or chatter return.

### 7.9 `sign.request.item`

Known useful fields:

```text
sign_request_id
role_id
partner_id
signer_email
state
signing_date
sign_link
document_link
signature
```

Implementation decision:

* Use it for completion diagnostics and signer-state visibility.
* Do not close registry from one signer item alone in multi-signer flows.
* Registry closes only when the overall request is fully signed.

## 8. F-0003 locked geometry

Actual tested Reviewer signature field:

```text
page: 1
posX: 0.073
posY: 0.591
width: 0.565
height: 0.075
alignment: left
required: true
name: Signature
```

Interpretation:

* This is the real placed field inside the F-0003 reviewer signature area.
* Rows with `page = -1` and negative coordinates are unplaced placeholders and must be ignored.
* Geometry should be treated as linked to the current locked F-0003 PDF layout.
* If F-0003 QWeb layout changes later, coordinates must be recalibrated.

## 9. Pass 5E-3A detailed scope

### Objective

Create and send a native Odoo Sign request from an already generated F-0003 PDF and store the resulting Sign request reference in the recruitment registry.

### In scope

* Add generic Sign tracking fields to `x_hr.recruitment_document` if not already present.
* Add one action/button path from F-0003 checklist or registry to create/send native Sign request.
* Validate prerequisites:

  * generated PDF exists;
  * reviewer exists;
  * reviewer has partner and email;
  * Reviewer role exists;
  * Signature field type exists;
  * matching registry row exists or can be found.
* Create dynamic `sign.template`.
* Create `sign.document` from generated PDF attachment.
* Create `sign.item` with locked F-0003 Reviewer geometry.
* Create `sign.send.request`.
* Create `sign.send.request.signer`.
* Call `send_request()`.
* Locate generated `sign.request`.
* Store Sign request reference and state on registry.
* Set registry/checklist state to signature requested.
* Post chatter messages on checklist and applicant where available.
* Keep manual signed-attachment fallback intact.

### Out of scope

* No QWeb/PDF changes.
* No F-0004 changes.
* No two-signer signing order.
* No direct signer-side signature submission.
* No `fill_sign` automation.
* No direct `sign.request.create()` as primary route.
* No archive/cleanup of dynamic templates.
* No completed-artifact registry closure yet unless split into 5E-3B.

## 10. Pass 5E-3B detailed scope

### Objective

Sync a linked native Odoo Sign request back into the recruitment registry and source F-0003 checklist after full signing completion.

### In scope

* Add registry sync action/button.
* Browse linked `sign.request` from registry fields.
* Read request state.
* Read signer items for diagnostics.
* If request is fully signed:

  * read completed document attachments;
  * classify signed PDF vs certificate;
  * link signed PDF as signed attachment;
  * link certificate if field exists;
  * mark registry signed;
  * mark source F-0003 checklist signed;
  * write completion date;
  * post chatter messages.
* If request is not fully signed:

  * update request state snapshot only;
  * keep registry as signature requested;
  * post or show clear message.

### Closure rule

Registry must not close as signed until the full `sign.request` is signed/completed, not merely because one `sign.request.item` is completed.

This is critical for F-0004 and later multi-signer forms.

## 15. F-0004 extension note

F-0004 is the first planned two-signer document:

```text
Applicant signer
HR Manager / Reviewer signer
```

Lessons from F-0003 must be applied before F-0004:

1. Multiple roles must each receive exactly one signer.
2. Registry must wait for full `sign.request` completion.
3. One completed signer item is not enough.
4. Signing order may be optional; it should not be introduced unless required by business/legal process.
5. Applicant partner/email normalization must be handled before send.
6. Certificate and signed PDF must be linked to registry.

## 16. Risk log

### Risk 1 — `send_request()` safe-eval behavior

Status: unresolved until 5E-3A run.

Mitigation:

* Wrap probe with clear `UserError` messages.
* Ignore return value.
* Search generated request after call.

### Risk 2 — direct `sign.item.create()` not accepted by template validation

Status: possible.

Mitigation:

* First try direct stored field creation.
* If rejected, switch to `sign.template.update_from_pdfviewer(...)` using UI-equivalent payload structure.

### Risk 3 — duplicate Sign request creation

Status: must be controlled.

Mitigation:

* If registry already has a linked active Sign request, do not create another unless explicitly reset/cancelled.

### Risk 4 — dynamic template accumulation

Status: acceptable for probe.

Mitigation:

* Do not clean up during 5E-3A.
* Consider archive/cleanup only after lifecycle locks.

### Risk 5 — artifact classification ambiguity

Status: deferred to 5E-3B.

Mitigation:

* Identify signed PDF vs certificate by filename and/or completed document metadata.
* If ambiguous, log and require manual fallback.

### Risk 6 — reference_doc/chatter return mismatch

Status: confirmed manual flow returns to Documents, not HR.

Mitigation:

* Do not rely on chatter return.
* Registry stores Sign request reference explicitly.
