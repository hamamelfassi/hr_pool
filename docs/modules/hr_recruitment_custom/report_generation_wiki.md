# MCEP Odoo SaaS QWeb Report Generation Wiki

## Purpose

This document defines the locked technical pattern for generating PDF reports in `hr_recruitment_custom` on Odoo.com SaaS 19.2.

It exists because F-0002 and F-0003 exposed multiple failure modes:
- missing paperformat caused huge physical PDF margins;
- whitespace inside `report_name` / `report_file` broke QWeb template lookup;
- layered CSS patches caused contradictory layout behavior;
- server actions cannot use forbidden Python imports such as `import base64`;
- QWeb loop counters were less reliable than stored fields or `t-out`;
- Arabic PDF rendering requires explicit UTF-8 meta tags and embedded Arabic fonts.

All future reports must reuse the clean working pattern below.

---

## 1. Required report action pattern

Every QWeb PDF report must have a matching `ir.actions.report` record.

Use this pattern:

```xml
<record id="action_report_xxx" model="ir.actions.report">
    <field name="name">Human Report Name</field>
    <field name="model">x_model_name</field>
    <field name="report_type">qweb-pdf</field>
    <field name="report_name">hr_recruitment_custom.report_template_xml_id</field>
    <field name="report_file">hr_recruitment_custom.report_template_xml_id</field>
    <field name="paperformat_id" ref="hr_recruitment_custom.paperformat_hr_applicant_tor"/>
    <field name="attachment_use" eval="False"/>
    <field name="print_report_name">'Report - %s' % (object.x_name or 'Applicant')</field>
</record>
```

### **Critical rules**

1. `report_name` and `report_file` must be single-line exact values.  
2. Do not allow XML formatters to split them over multiple lines.  
3. Always set `paperformat_id`.  
4. Always set `attachment_use=False` for reports generated by custom server actions.  
5. The `report_name` value must exactly match the QWeb template external ID.

Bad:

```
<field name="report_name">
   hr_recruitment_custom.report_template_xml_id
</field>
```

Good:

```
<field name="report_name">hr_recruitment_custom.report_template_xml_id</field>
```

## **2\. Paperformat dependency**

The compact PDF layout depends on:

```
<field name="paperformat_id" ref="hr_recruitment_custom.paperformat_hr_applicant_tor"/>
```

Without this, Odoo may apply default paper margins, causing a large blank top area before the report header.

This was the root cause of the major F-0003 page-margin failure.

---

## **3\. Required QWeb template skeleton**

Use this structure:

```
<template id="report_template_xml_id">
   <t t-call="web.html_container">
       <t t-foreach="docs" t-as="o">
           <head>
               <meta charset="UTF-8"/>
               <meta http-equiv="Content-Type" content="text/html; charset=UTF-8"/>
           </head>

           <div class="page">
               <style>
                   /* Embedded fonts first */
                   /* One clean report stylesheet only */
               </style>

               <div class="tor-doc mcep-one-page report-specific-class">
                   <div class="tor-header-fixed">
                       <!-- logo + metadata -->
                   </div>

                   <!-- report body -->
               </div>
           </div>
       </t>
   </t>
</template>
```

### **Critical rules**

1. Always include UTF-8 meta tags.  
2. Put the fixed header inside the main `tor-doc` wrapper unless there is a proven reason not to.  
3. Do not accumulate multiple cleanup CSS blocks.  
4. Use one clean stylesheet per report.

## **4\. Arabic fonts**

Arabic QWeb PDFs must use embedded inline fonts.

Current working family names:

```
@font-face {
   font-family: 'TORArabicRegularInline';
   src: url('data:font/ttf;base64,...');
   font-weight: 400;
   font-style: normal;
}

@font-face {
   font-family: 'TORArabicSemiBoldInline';
   src: url('data:font/ttf;base64,...');
   font-weight: 600;
   font-style: normal;
}
```

Use these in Arabic text:

```
font-family: 'TORArabicRegularInline', 'Noto Naskh Arabic', 'Amiri', 'Scheherazade New', 'DejaVu Sans', Tahoma, sans-serif;
```

Use semibold for headings/labels:

```
font-family: 'TORArabicSemiBoldInline', 'TORArabicRegularInline', 'Noto Naskh Arabic', 'Amiri', 'Scheherazade New', 'DejaVu Sans', Tahoma, sans-serif;
```

## **5\. Logo/header pattern**

Use the embedded base64 logo pattern from the working F-0002/F-0003 templates.

Do not replace the logo with text such as `MCEP`.

Use:

```
<img class="tor-logo"
    src="data:image/png;base64,..."
    alt="Marsellia"/>
```

Header metadata should be small and fixed:

```
<div class="f000x-header-meta">

   مرجع المستند: <span t-field="o.x_document_reference"/><br/>
   الحالة: <span t-field="o.x_state"/>
</div>
```

## **6\. Server action PDF generation pattern**

Odoo SaaS server actions use safe-eval. Avoid imports.

Do not use:

```
import base64
'datas': base64.b64encode(pdf_content)
```

Use:

```
report_service = env['ir.actions.report'].sudo()

pdf_content, _content_type = report_service._render_qweb_pdf(
   'hr_recruitment_custom.action_report_xxx',
   [rec.id]
)

attachment = env['ir.attachment'].sudo().create({
   'name': filename,
   'type': 'binary',
   'raw': pdf_content,
   'res_model': 'hr.applicant',
   'res_id': applicant.id,
   'mimetype': 'application/pdf',
})
```

### **Critical rules**

1. Call `_render_qweb_pdf(report_action_xmlid, [record_id])`.  
2. Do not call `report._render_qweb_pdf([record_id])`.  
3. Use `raw: pdf_content`, not base64 imports.  
4. Write generated attachment fields after attachment creation.  
5. Update registry row in the same server action.

## **7\. Dynamic rendering rules**

### **Static Arabic/English labels**

Use direct text in the template, with UTF-8 meta tags and embedded fonts.

### **Same-model dynamic fields**

Use:

```
<span t-field="o.x_field_name"/>
```

### **Linked model joins**

Use:

```
<span t-field="o.x_applicant_id.partner_name"/>
<span t-field="o.x_applicant_id.job_id"/>
```

### **Computed values / expressions**

Prefer:

```
<span t-out="expression"/>
```

Avoid unnecessary `t-esc` unless already proven in the target Odoo version/report.

### **Sequence values**

Preferred order:

1. Use a stored field with `t-field`, as in F-0002:

```
<span t-field="line.x_sequence"/>
```

3. 

4. If a display sequence must be calculated, use `t-out`:

```
<span t-out="counter"/>
```

6. 

7. Avoid relying on `line_index` unless proven in the rendered PDF.

## **8\. Table/layout rules**

Use table-local classes and one clean CSS block.

Preferred table pattern:

```
<table class="tor-table f000x-table">
   <thead>...</thead>
   <tbody>
       <t t-foreach="lines" t-as="line">
           <tr>
               ...
           </tr>
       </t>
   </tbody>
</table>
```

Set row height on cells, not only on `<tr>`:

```
.f000x-table tbody td {
   height: 34px;
}
```

`wkhtmltopdf` may ignore or inconsistently apply `min-height` on table rows.

---

## **9\. Checkbox rendering**

Use box spans, not Unicode checkbox glyphs, for predictable PDF rendering:

```
<span class="mcep-score-box">
   <span t-if="condition">X</span>
</span>
```

CSS:

```
.mcep-score-box,
.f000x-box {
   display: inline-block;
   width: 11px;
   height: 11px;
   line-height: 10px;
   border: 1px solid #111;
   text-align: center;
   font-size: 8px;
   font-family: DejaVu Sans, Tahoma, sans-serif;
}
```

## **10\. Signature area**

Reports intended for Odoo Sign must provide a stable empty cell.

Example:

```
<tr>
   <th>التوقيع<br/><span class="tor-ltr">Signature</span></th>
   <td class="f000x-sign-cell"></td>
</tr>
```

CSS:

```
.f000x-sign-cell {
   height: 90px;
}
```

The actual Sign field geometry is configured later in the signing/signature template layer, but the PDF must provide enough stable blank space.

---

## **11\. Anti-patterns to avoid**

Do not:

* stack repeated CSS cleanup blocks;  
* use fake text logos;  
* omit `paperformat_id`;  
* split `report_name` or `report_file`;  
* use forbidden imports in server actions;  
* rely on default Odoo PDF margins;  
* patch layout blindly before checking report action/paperformat;  
* print internal implementation notes into formal PDFs;  
* mix multiple table-width mechanisms unless necessary.

## **12\. Preflight checklist for every new report**

Before build/install:

```
grep -n "paperformat_id\|attachment_use\|report_name\|report_file" \
 modules/hr_recruitment_custom/report/<report_action_file>.xml
```

Confirm:

* `report_name` and `report_file` are exact single-line XML IDs.  
* `paperformat_id` is present.  
* `attachment_use=False` is present.

Then:

```
python3 - <<'PY'
from pathlib import Path
import xml.etree.ElementTree as ET

for f in [
   "modules/hr_recruitment_custom/report/<template_file>.xml",
   "modules/hr_recruitment_custom/report/<action_file>.xml",
]:
   ET.parse(Path(f))
   print(f"{f} parses cleanly.")
PY
```

Then:

```
./scripts/build_module_zip.sh hr_recruitment_custom
```

And verify the zip, not only the working tree:

```
unzip -p dist/hr_recruitment_custom.zip hr_recruitment_custom/report/<action_file>.xml \
 | grep -n "paperformat_id\|attachment_use\|report_name\|report_file"
```
